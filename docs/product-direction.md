# 产品方向与开发约定

基线日期：2026-10-07

正式名称：星愿（2026-10-19 所有者确认）；原项目代号 Habit Checkin。

我们要做一款既能独立使用，也能与熟人相互陪伴的目标打卡 App。
一个人可以管理目标、打卡、设置提醒和回顾记录；愿意时，再与两三位异地情侣或好友
组成私密小组，自主分享进展，在轻量互动中相互督促、理解和陪伴。
**个人体验是基础，小组陪伴是可选扩展，不能要求先组队才能正常使用。**
**它不是排行榜、公开社交平台，也不是要求所有人完成同一套任务的管理工具。**

本文是后续设计、开发和验收的共同依据，不代表所列功能已经实现。
“已确认方向”来自已有讨论；“首版设计草案”是拟采用的实现范围，可以在使用中调整；
“待确认事项”不能被当成已经作出的决定。

执行细节分别见[竞品研究与实测记录](competitor-research.md)、
[首版技术方案](architecture.md)和[开发工作量与交付计划](delivery-plan.md)。
本文件管理产品边界，技术文档管理推荐方案与验证关卡，排期文档管理工作量与交付条件；
竞品资料调研不等同于实际安装体验。

## 已确认方向

| 事项 | 约定 |
| --- | --- |
| 主要使用者 | 独自管理目标的个人，以及希望相互陪伴的两三位异地情侣或好友 |
| 主要价值 | 一个人能做好目标记录与提醒；自愿组队后，通过分享促进相互监督、成长和沟通 |
| 目标关系 | 每个人的任务可以完全不同，不要求共同计划或共同完成 |
| 互动方式 | 鼓励与了解优先，不做排名，不以比较制造压力 |
| 隐私边界 | 只能看到对方主动选择展示的内容 |
| 基础能力 | 个人目标、打卡、提醒和回顾；登录后可使用云端存储，小组共享可选 |
| 视觉与激励 | 清新、轻量的界面，适度的个人成就反馈 |
| 平台顺序 | 先 iOS，再扩展 Android；鸿蒙列为后续适配目标 |
| 暂不开发 | 浏览器版和 PC 版产品 |
| 工程目标 | 从开始就在 GitHub 管理代码，逐步形成可用于简历展示的完整项目 |
| 迭代方式 | 先采用简单合理的规则，再根据实际使用感受改进 |

“两三人”描述小组使用场景，不是使用 App 的最低人数，也不等于已经确定人数上限。
鸿蒙适配需要单独验证技术方案，不能把“已使用 Flutter”当成已经兼容。

## 典型使用场景

### 个人使用

甲不邀请任何人，直接建立“每天阅读”的习惯和“周五整理资料”的单次任务，
按自己的需要设置提醒，完成后打卡，偶尔撤销误操作，并在回顾中查看记录。
这是一种完整、长期有效的使用方式，不是等待组队的临时状态。

首版拟支持不登录的本地使用。需要云端保存时再登录，登录后仍然可以只供自己使用，
不必创建小组。退出小组不应删除本人的目标、历史或个人提醒设置。

### 自愿组队

甲今天想阅读，乙想跑步，丙准备面试。他们加入同一个私密小组，
各自决定展示哪些目标。甲可以分享阅读进度，但保留自己的私人笔记；
乙尚未完成跑步，也可以发布一句“今天下雨，准备改成室内运动”。

成员能回应彼此的分享，但不能替对方打卡或修改目标。
某个人今天没有记录，不代表他失败、偷懒或影响了其他人的成绩。
加入小组是在原有个人记录之上开启分享，不另建一套必须重新录入的目标。

## 不轻易改变的产品原则

1. **单人体验完整。** 个人目标、打卡、提醒和回顾不依赖小组，不因未组队而受限。
2. **各自成长，不做竞争。** 不做排行榜、成员完成率比较、关系分数或连带惩罚。
3. **分享出于主动。** 新目标默认私密；加入小组不等于公开全部目标和历史。
4. **打卡与表达分开。** 完成任务不强制写动态，发布动态不强制完成任务。
5. **鼓励不变成催促。** 支持本人主动设置的提醒，不以羞辱文案、强制提醒或公开缺席名单推动使用。
6. **真实状态优先。** 离线、未同步和没有完成是不同状态，不能混为一谈。
7. **先把小场景做好。** 新功能必须服务于个人记录或熟人间的理解与支持。
8. **技术服务于体验。** 技术亮点来自可靠实现，不为简历堆砌无关框架和功能。

## 首版设计草案

下面是下一阶段的设计起点，不是已经上线的功能，也不冻结所有交互细节。

### M1 执行规则基线

2026-10-09，所有者启动 [GOAL.md](../GOAL.md) 所定义的 M0 + M1 任务。
以下是本轮采用的实现规则，不代表相关功能已经实现，也不扩展到云端或小组阶段。
具体边界与逐项验收以 Goal 第 5 至 7、10、14 章为执行清单，
实际进度见 [M1 实施与验收记录](m1-delivery.md)。

- 每日、指定星期和单次任务；重复习惯从创建日开始，星期一为周起点。
- 按设备本地日历日计算今天，历史所属日期与事件时间分开保存，不随时区移动。
- 习惯同一目标同日唯一，单次任务全局最多一个有效完成；仅可撤销当前日期的完成。
- 不做补签、历史修改或未来打卡。单次逾期仍在待办，实际完成日与原计划日期分开。
- 重复规则修改次日生效，既有日期不重算；名称、规则和计划日期保留历史含义。
- 归档停止未来待办和提醒，但保留历史；M1 不提供恢复归档或永久删除。
- 提醒默认关闭，每个目标执行日最多一次，单次任务只在计划日提醒，不自动每日催促。
- 完成取消本次尚未触发提醒，未来保留；撤销仅恢复仍在未来且未结束的本次，不补发。
- 通知文案不显示目标私密详情。授权、偏好与实际调度状态分开；拒绝权限仍可记录。
- 夏令时缺失时刻采用同日下一个有效时刻，重复时刻只取第一次；具体系统语义必须验证。
- 有限提醒覆盖、目标数量或后台/时区限制需要用户明确批准；本轮已确认方案见下文
  “个人提醒”的 2026-10-10 决定，不据此批准其他降级。

M1 已按所有者调整后的标准收口：A18 72 小时观察撤销，其余缺少补充真机证据的项
记录“所有者报告完成，执行者未取得可核实证据”。这不将原 G2 或设备证据扩大为通过。
详见 [M1 收口记录](m1-delivery.md#e024-所有者收口决定2026-10-10)。

### 页面组织

| 页面 | 主要内容 | 边界 |
| --- | --- | --- |
| 今天 | 自己的习惯、单次任务、打卡、撤销、提醒设置和记录入口 | 无需组队即可使用，默认进入可操作的个人页面 |
| 我们 | 已授权分享的目标与进度、简短动态、回应与鼓励 | 不展示成员排名或未经分享的私人信息 |
| 回顾 | 个人历史、成长记录和少量成就 | 不演变成与其他成员的比较报表 |
| 头像入口 | 账号、小组、隐私和设置 | 关键共享设置应容易找到 |

没有加入小组时，个人页面仍是完整的主体验；“我们”提供不打扰使用的可选入口，
不反复弹窗催促邀请好友，也不让大面积组队提示占据个人首页。
演示数据与真实成员数据必须能区分。
界面以浅色背景、清晰文字和少量薄荷绿、珊瑚色点缀为起点。
颜色和组件细节可以调整，但保持轻量、易读，兼顾 iPhone 11、小屏和大字体。

### 功能范围

| 首版能力 | 拟定范围 |
| --- | --- |
| 个人目标 | 支持重复习惯和单次任务，能新增、编辑、归档 |
| 打卡 | 当日完成、撤销、查看历史；先不做复杂计分和验证机制 |
| 个人提醒 | 本人可按目标开启或关闭、设置时间；首版拟采用本地通知，不依赖组队或云端 |
| 本地保存 | 个人记录在重启后仍存在，离线时仍可记录 |
| 账号 | 默认方案为邮箱验证码登录；本地个人使用不强制登录，邮件投递与迁移须先验证 |
| 云端保存 | 登录后保存个人数据，无需加入小组；显示同步中的状态与失败情况 |
| 私密小组 | 拟先支持一个小组的创建、邀请、加入和退出 |
| 选择性共享 | 按目标决定是否向小组分享，能查看并撤销共享 |
| 轻量交流 | 分享打卡下回复；2026-10-21 已批准两人文字/图片私聊，按专项 Goal 实施，不做群聊或音视频 |
| 回顾与成就 | 个人历史和少量鼓励型成就，不建立成员之间的排名 |

首版完成的含义是上述体验贯通，不是每项都拥有大量设置。
邮箱验证码、一个小组、页面命名等属于可调整方案，不是永久限制。

### 基础规则

- 先以简单的完成和未完成状态验证流程，不把复杂计数、计时或自动识别作为前置条件。
- 同一任务在同一所属日期不能因为重复点击或网络重试被重复打卡。
- 本人可以撤销自己的打卡；他人不能修改这条记录。
- 一次完成不必附带文字，尚未完成也可以分享一条进展。
- 共享目标不自动公开私人备注、照片或过去全部记录。
- 修改重复规则或归档目标时，保留历史记录的含义，不悄悄重算过去。
- 跨日、时区、补签和休息日的具体规则在实现历史功能前确定并补入本文。
- 成就以个人成长为对象，不用他人的缺席扣分，也不设置关系等级。

### 个人提醒

2026-10-10 执行决定：所有者在获知有限预排的影响后，授权 AI 选定合理方案。
M1 采用最近优先、最多 64 个系统名额的单次提醒，启动/回前台/变更时核对并补排，
不限制创建目标数；明确显示每个目标的覆盖末次、下一未覆盖日期和容量不足。
长期不打开可耗尽，后台补排不保证，关闭期间时区变化在重开后校正。
这是范围内已确认的限制，不是实现或真机验收完成，详见 Goal 第 7 章。

提醒已纳入首版个人体验，不再作为“是否需要”的待定功能。以下是实现草案：

- 由本人主动开启并设置时间；在用户启用提醒时请求通知权限，而不是以授权作为使用门槛。
- 拒绝通知权限或关闭提醒后，仍能正常管理目标、打卡和查看记录。
- 优先在手机本地安排提醒，不要求登录、加入小组或由服务器在线触发。
- 改时间、关闭提醒、归档或删除目标时，同步更新或取消相关待触发提醒，避免旧提醒残留。
- 已完成当次任务后取消该次尚未触发的提醒，不因此取消未来重复任务的提醒。
  撤销打卡后的恢复规则、跨日和时区变化的处理在 M1 实现前明确。
- 个人提醒只面向本人，不自动转成发给伴侣或好友的催促消息。
- 通知文案拟默认不显示私密目标详情；通知预览方式、提醒频次和具体调度方案在 M1 中确定。

提醒需单独覆盖通知授权、取消和修改后的真机验证，不能只凭页面开关判断已实现。

## 隐私与小组权限

这是核心功能的一部分，不能等上线前再补。

| 数据或操作 | 本人 | 同组成员 | 非成员 |
| --- | --- | --- | --- |
| 私密目标、打卡和私人备注 | 可管理 | 不可访问 | 不可访问 |
| 主动共享的目标及授权进度 | 可管理和撤销共享 | 可查看授权范围 | 不可访问 |
| 面向小组发布的文字动态 | 可管理自己的内容 | 可查看并回应 | 不可访问 |
| 修改别人的目标或打卡 | 不适用 | 不允许 | 不允许 |
| 回复与鼓励 | 可管理自己的内容 | 可提交自己的回应 | 不允许 |

小组管理员不因为身份而获得查看私密目标或修改他人打卡的权限。
成员只看到主动发布或共享的内容；汇总数字也不能泄露未共享目标的数量、名称或完成情况。

权限必须在服务端执行，不能只在手机界面隐藏按钮。新成员加入、成员退出、
撤销共享以及登录账号切换，都要覆盖权限和缓存的清理。
失去权限后的请求必须被拒绝，客户端得知变更后应移除不再可见的缓存。

撤销共享不能追回别人已经看到、截图或自行保存的内容。动态、回复、历史内容在
退出小组或删除账号后如何保留，必须在开放真实多人使用前确定并向用户说明。
邀请有效期、新成员能否看到旧动态，也不能采用未经确认的宽松默认值。

## 前后端分工与部署

| 部分 | 本项目中的职责 | 运行或存放位置 |
| --- | --- | --- |
| Flutter 手机端 | 页面、交互、本地记录、个人提醒、同步状态和调用接口 | 开发时在模拟器或真机；使用时安装在手机 |
| 本地存储 | 保存个人记录及待同步修改，支持断网使用 | 用户手机内部 |
| 后端服务 | 身份验证、小组成员关系、授权检查、同步和互动规则 | 后续选择的云端环境 |
| 云端数据库 | 保存账号关联的数据、目标、打卡、共享关系和互动 | 后端使用的数据库环境 |
| GitHub | 代码、文档、版本记录和自动检查 | 已建立的私有代码仓库 |

GitHub 不是在线业务后端，也不存放真实打卡数据、私人日记或生产密钥。
首版个人目标、打卡和本地提醒不以部署后端为前提；云端保存与小组共享再接入后端。
手机端和云端分别发布，不需要为了移动端再建设一个浏览器产品。
应用分发、签名与商店发布在需要邀请外部试用时单独核实和安排。

### 技术执行基线

- 已采用 Flutter 和 Dart，现有工程只有 iOS 目标。
- 首版推荐 Riverpod 管理状态、Drift 与 SQLite 保存本地数据、本地通知插件处理个人提醒。
- 后端默认推荐 Supabase Auth 与 PostgreSQL，配合服务端权限；2026-10-10 已按所有者确认
  创建免费开发项目，尚未接入 App、通过 G3 或购买付费服务。
- 同步采用本地待发送队列、幂等写入和版本检查，不依赖 SDK 自动解决离线冲突。
- 核心四个包在独立目录完成依赖解析；原生插件、通知、网络及邮件还须通过技术文档中的关卡。
- 云端资源创建前确认费用、实际网络、数据位置和学习目标；失败时重估后端，不影响个人版推进。
- 鸿蒙方案后续单独评估，不为尚未验证的适配提前重构整个项目。
- 优先采用清晰、可测试的结构；现阶段不引入微服务或复杂基础设施。

### 同步要求

本地记录与云端确认必须区分。个人记录应先能安全落在本地，再尝试同步；
联网失败应显示待同步或失败状态并允许重试，不能假装已发送给对方。
多人互动只有经过服务端认证和授权后才成为对方可见的数据。

同步设计必须处理重复请求、撤销和删除、账号隔离，以及多设备修改冲突。
具体冲突规则在接入同步前确定，不能默认用后一次上传静默覆盖所有内容。
退出登录或加入新小组时，不自动上传或共享原账号、原小组的私人数据。

## 首版验收场景

### 个人使用验收

1. 新用户不登录、不组队，即可建立习惯和单次任务、打卡、撤销以及查看自己的历史。
2. 断网时仍可记录，重启后数据保留；首页不被组队提示占据，也不要求邀请好友解锁个人功能。
3. 在真机授予通知权限后，设置的本地提醒可触发；断网且 App 不在前台时也要验证。
4. 修改提醒时间、关闭提醒、归档或删除目标后，旧的待触发提醒不再出现；
   完成当次任务后不再被该次提醒催促，未来重复任务仍保留其提醒计划。
5. 拒绝通知权限仍可正常打卡，界面能说明提醒未启用，不把此状态误报为已设置成功。
6. 用户登录但不加入小组，也能保存和同步自己的数据；本地数据迁移须遵循后续确认的规则。
7. 加入或退出小组不丢失自己的目标、历史和个人提醒，也不擅自扩大分享范围；
   退出时仍须撤销相应的小组访问权限。

### 自愿组队验收

1. 甲与乙登录不同账号，加入同一个邀请制小组，各自拥有不同的目标。
2. 甲有一个共享目标和一个私密目标；乙只能看到前者，包括汇总中也不泄露后者。
3. 甲完成共享目标，乙在同步后看到进度，并可以回应；甲的私人备注仍不可见。
4. 乙未完成目标也能发一条动态；甲不写动态也能完成打卡。
5. 甲断网记录后重启 App，记录仍在；恢复网络重试不会产生重复记录或回应。
6. 甲撤销共享或乙退出小组后，乙的新请求无法再获取相关受限数据。
7. 未登录用户、非成员丙以及试图修改甲记录的乙，直接调用接口也会被拒绝。
8. 切换账号后不显示上个账号的私密数据，也不把其待同步记录上传到新账号。
9. 任一成员缺席不会扣除其他人的成绩，不出现排名、羞辱提醒或关系评分。
10. 核心流程在 iPhone 真机可操作，小屏和大字体下没有遮挡关键按钮。

## 防止方向偏移的工作方式

每次开始一个功能前，先说明它对应哪个使用场景、属于哪个里程碑、如何验收。
小型交互细节可以在既定范围内迭代；改变隐私默认值、加入竞争机制、
扩大平台或社交范围、产生付费资源的决定必须先重新确认。

新增想法统一记录以下内容，不直接替换当前任务：

| 字段 | 要回答的问题 |
| --- | --- |
| 用户问题 | 谁在什么场景遇到了什么困难 |
| 预期价值 | 如何改善个人记录或熟人之间的支持与理解 |
| 隐私影响 | 谁会新增看到什么内容，是否需要新的授权 |
| 范围与代价 | 属于当前里程碑还是后续，增加哪些维护或使用成本 |
| 验收标准 | 怎样证明这个功能真的解决了问题 |
| 决定 | 本期实现、后续候选或不做，以及原因 |

方向发生变化时，先与项目所有者确认，再同步修改本文和受影响的验收标准。
每次交付区分“已实现”“已验证”和“仍是计划”；不把测试通过说成真机已验证。
有意义的改动提交并同步到 GitHub，不提交密钥、证书、真实个人数据或构建产物。
