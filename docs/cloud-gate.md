## 待执行部署

配合事项已一次性告知，见 [账本](phase2-delivery.md#配合事项p2-前一次性清单)。
所有者完成 CLI 授权后，执行者先核对账号、项目名、区域与本机 URL 对应，
确认仅操作已获授权 dev 环境且没有未知业务对象，再链接、查看迁移、dry-run。
项目 ID 不是密码，但也不在文档中复制真实内部配置。

```sh
# 所有者本人执行；不要向聊天粘贴 token。
supabase login

# 下列由执行者在核对项目后运行；替换占位符，不照字面执行。
supabase link --project-ref <verified-dev-project-ref>
supabase migration list --linked
supabase db push --linked --dry-run --skip-vault
supabase db push --linked --skip-vault
supabase db query --linked --file supabase/tests/g3_probe_authorization.sql
```

不在命令参数中传数据库密码；必要时由所有者在安全提示中输入。
不运行 `db reset`、`--include-seed`、`supabase start` 或未审核迁移，
不安装 Docker。CLI `db query --help` 已确认本机版本支持通过 Management API
对 linked 项目执行 SQL 文件；这只是命令能力核对，不是执行成功证据。
迁移必须走 CLI 的迁移记录，不能改用 query 直接建表跳过迁移管理。

迁移中的 `g3_probe_*` 对象仅存合成 UUID 与整数，没有目标标题、历史或提醒。
表开启且强制 RLS；认证账号只能直接读取本人行，写入/删除经受控函数，
owner 取自 `auth.uid()`，不接受客户端指定。其他账号不能修改或删除原行。
正式目标的完整幂等/revision RPC 尚未实现，该探针不替代 S14 的最终业务测试。

SQL 测试在事务内创建随机合成 auth 用户，模拟 A/B/anon 角色，检查允许与拒绝；
成功以 rollback 撤销全部测试用户和行，失败则事务回滚。测试没有删除真实账号的操作。
只有真实执行得到 `G3_SQL_ROLE_PROBE_PASS` 才能记录这一层通过。
通过也只证明数据库角色行为，仍须另以真实签发的 A/B 用户 JWT 直接调用 API。

## 真实 API 工具

`tool/run_cloud_gate.dart` 是 Mac 上的临时诊断工具，不是正式 App 登录/同步实现。
它使用 Dart 标准 HTTP 客户端请求 Auth 和 Data API；不安装新 SDK 或保存会话。
接口契约复核于 2026-10-11，参考
[Supabase Auth OpenAPI](https://github.com/supabase/auth/blob/master/openapi.yaml)。
正式 App 的 `supabase_flutter` 接入仍在 G3 通过后实施。

先完成已列出的 CLI/迁移、SMTP 和双邮箱准备，由所有者核对模板能显示数字验证码，
不能把只收到 magic link 当作已经验证邮箱验证码登录。工具不修改后台邮件设置。
执行者不代登录所有者的后台、邮箱或 Apple 账号；实际收信和读码仍由所有者操作。

```sh
# 默认/帮助模式不读取配置、不联网、不发信。
dart run tool/run_cloud_gate.dart --help

# 在本机交互式终端手动运行。替换项目占位符，不把邮箱/token 放在参数里。
# 默认只使用已有测试账号；仅首次明确要创建合成账号时加 --create-test-users。
dart run tool/run_cloud_gate.dart --live --project-ref=<verified-dev-project-ref>
```

Live 模式要求显式项目 ID 与本机公开配置一致，检查配置 0600/Git 排除，
且必须是交互式终端。首次测试先用匿名请求检查最小表已经可访问到权限边界；
表不存在、key 不可用或匿名异常可读时，在发信前失败。
所有者分别输入两个测试邮箱和收到的验证码，均关闭终端回显；
每个输入邮箱只发送一次验证码，不自动重试或批量发信。随后分别刷新会话、
核对 `/user` 返回的真实账号 ID，再执行下方权限矩阵中的实际 API 项。
JWT 不从剪贴板/文件读取，不手工解码后就当作认证成功，也不使用 service_role。
“无 subject 的认证角色”仅 SQL 角色测试覆盖，不能伪造真实签名 JWT 代测。

工具先确认 A、B 都能读写各自合成行，再验证跨账号和未登录行为。
真正的权限拒绝须匹配预期 HTTP 状态及 SQL `42501`；
不存在表/函数、失效 token、5xx、限流或网络中断不能算“越权被拒”。
带多余 owner 参数的 RPC 另外要求 `PGRST202` 签名不匹配；
这是对现有最小函数签名的测试，不代表最终同步 RPC 已验证。

每次请求最多 20 秒、响应最多 64 KiB、不跟随重定向，不关闭 TLS 校验。
报告只保留固定路径、认证/匿名标签、HTTP 状态、白名单错误码、行数和耗时，
不保留头、请求/响应正文、邮箱或 token。检查结果通过请求索引关联脱敏请求摘要。
每次请求使用新的 HTTP 连接，包含连接开销；这些诊断耗时不是手机或生产 SDK 基准。

在第一次业务写入前，工具将本 run 的三个随机记录 ID 和两个用户 ID 写到
被忽略的 `build/cloud-gate/<run-id>.json`；目录 0700、文件 0600，
不含账号凭据或目标内容。结束时更新脱敏报告。剩余检查因前置失败未运行时明确标
`not_run`；只有全部 20 个 API 检查与记录清理通过才给通过结果，退出会话失败也会
令命令退出非零。会话只从内存使用，正常退出执行 `scope=local` 注销，
不注销该账号的其他设备。
最终报告先写入同目录的 0600 临时文件并 flush，再替换原文件，避免直接截断
清理清单；中断遗留的 `.pending-*` 文件不是完成证据，恢复仍读取原 run 文件。

清理只针对本 run 的三个 ID，不遍历或清空整个表。收到成功前断网/进程终止时，
保留原 manifest，以同一两个测试账号在终端运行：

```sh
dart run tool/run_cloud_gate.dart --live --project-ref=<verified-dev-project-ref> --cleanup=<run-id>
```

恢复先核对项目/run/两个真实账号，仍只清理这三个合成 ID；权限发生回归时不被
首次匿名预检阻断。恢复结果写入新的 `<run-id>.cleanup-<uuid>.json`，
原始失败证据不覆盖，也不把“清理成功”改写为原权限测试通过。
硬中止不能保证会话已注销；必要时由所有者精确清理测试账号的残留会话。
工具不删除 Auth 账号，账号最终清理仍按下方规则。

**当前 live 模式未执行。** 诊断工具的自动测试使用合同替身、本机 loopback
HTTP 服务器及临时文件，验证判定、隐私、防重定向、大小/超时上限及清理，不能证明
托管 Supabase 的实际协议、邮件或 RLS 正确。
这个 Mac 工具即使未来通过，也不能代替手机两类网络各 20 次登录/刷新/读/写、
双邮箱投递时间、过期/错码/重发限流测试或正式目标的 S14。

## 权限取证矩阵

下面所有条目当前均为 **未执行**。用实际 API 状态、脱敏断言和行数补结果，
不能因 HTTP 200 就认定通过；RLS 隐藏他人行时，正确结果可以是空集合。

| 身份 / 操作 | 必须结果 |
| --- | --- |
| A 经 RPC 新建/改整数，再读取 | owner 为 A，仅一行，值一致 |
| A 直接 insert/update/delete 表 | 拒绝，不能绕过受控写入 |
| B 查询 A 的 ID | 无 A 的行和字段 |
| B 经 RPC 覆盖 A 的 ID | 拒绝，A 的行保持原样 |
| B 经删除函数删除 A 的 ID | 返回 false，A 的行仍在 |
| B 创建和查询自己的另一个 ID | 成功，不能混入 A 的数据 |
| 伪造 owner_id 直接写表 | 拒绝 |
| 为 RPC 添加 owner_id 参数 | 拒绝不存在的函数签名，不接纳额外 owner |
| 只有 publishable key、无用户会话 | 读和函数调用均拒绝 |
| 无 subject 的认证角色 | 写入和删除均拒绝 |
| A 删除自己的测试行 | 成功，之后无法读到 |

SQL 测试通过后仍要检查公开 Data API 的 grants、RPC 签名与实际 token 行为，
以及错误没有泄露他人数据。不能用管理员权限发出的成功请求代替普通用户测试。

## 网络与邮件取证

仅在隔离测试构建中使用合成身份；所有者正常安装不登录测试账号或上传真实访客数据。
网络由所有者切换，执行者记录当时网络而非从电脑的连通性推断手机。

| 手机网络 | 登录 | 刷新会话 | 读 | 写 |
| --- | --- | --- | --- | --- |
| 实际 Wi-Fi | 未执行，至少 20 次 | 未执行，至少 20 次 | 未执行，至少 20 次 | 未执行，至少 20 次 |
| 实际移动网络 | 未执行，至少 20 次 | 未执行，至少 20 次 | 未执行，至少 20 次 | 未执行，至少 20 次 |

每次记录网络标签、操作类型、样本序号、开始时间、耗时、成功与否、脱敏失败类别。
不记 token、验证码、邮箱全文或响应正文。原始摘要应能复算成功率；
成功样本延迟用 nearest-rank 计算 p50/p95，失败次数与超时另外列出，
不把丢失/失败样本从成功率分母移除。每种网络默认成功率须不低于 95%，
并列出各操作分项；恢复后数据正确且无重复。当前没有任何测量值。

登录必须是真实邮箱验证码校验成功，不把“发送成功”、查询会话或 token 刷新计作登录。
至少 40 次成功登录取证需要相应的 owner 读码与投递窗口；按实际限流安排，
不批量轰炸邮箱或私自提高限额。错码、过期和重发限流另做负向测试。
两个经所有者提供的邮箱各记录到达耗时、垃圾箱状态和最终登录结果，
均应在 2 分钟内收到且可登录；未取得这些证据前保持等待条件。
