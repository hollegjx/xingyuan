# 个人账号与同步设计

2026-10-11；对应第二阶段 P1、S04，执行依据为 `GOAL-phase2-sync.md` 第 3、4 章。
这是实施规格，不代表功能或 G3 已通过。正式云端接入必须等待 G3。

## 边界与依赖

- 保留 Flutter、Riverpod、Drift/SQLite 和现有提醒协调器。
- 本地数据库仍是页面的直接数据源；云端失败不回滚已落盘记录。
- 未登录的本机访客不初始化云端会话，不发送目标、打卡或遥测。
- 同步范围仅为目标、标题版本、计划版本、打卡/撤销、归档。
  提醒偏好、系统通知 ID 和调度账本不上传；新设备恢复后提醒默认关闭。
- 2026-10-11 查询 pub.dev：`supabase_flutter` 最新稳定版为 2.18.2，
  `uuid` 为 4.6.0。已用 pub.dev JSON 元数据复核，发布日期分别为
  2026-10-09、2026-07-15。正式引入时验证解析，锁定 `pubspec.lock`；
  先不升级全局 Flutter 3.47.6。SDK 默认会话存储不得直接当作 Keychain。
- `supabase_flutter` 只负责认证和接口，不替代下述 outbox、冲突和幂等协议。

## 同步单位与 ID

同步单位为一个“目标聚合”：目标的不可变创建信息、全部标题/计划版本、
全部打卡状态（含撤销的 false 记录）和归档信息。提醒不在聚合内。
本阶段没有删除历史的操作：请求遗漏一个已存在的历史键不代表删除，
服务端保留该键；修改已有同键记录必须经过 revision 检查或明确冲突解决。
规范响应返回保留后的完整集合，客户端不能用稀疏请求覆盖整段历史。

每个目标在客户端生成稳定 UUID v4，跨设备使用该 UUID；
现有 SQLite 自增 `id` 继续作为内部关联键，不重编号既有记录。
子记录以“目标 UUID + effective_day / occurrence_key”组成全局自然键，
不因上传、拉取或重试重复生成历史行；单次任务始终使用 `once` occurrence。
服务端对同一目标的修改串行检查 revision，本阶段不做多人编辑或 CRDT。

本地身份使用 `guest` 或 `user:<auth-user-uuid>`。账号 ID 只能来自验证后的会话；
用户不能通过表单指定 owner。现有其他测试 owner 不被当作可上传账号。
全局 ID 不编码姓名、邮箱、日期或设备标识。

## 本地 schema v3

| 表 | 变化/用途 | 约束 |
| --- | --- | --- |
| goals | 增加全局 UUID；保留全部旧列 | 全局唯一且非空；原 id 与 kind 约束保留 |
| goal_titles / goal_schedules / check_ins | 原值和键不变 | 通过 goal_id 关联全局目标 |
| goal_reminders | 保持设备本地偏好 | 不上传、不从远端覆盖 |
| reminder_occurrences | 增加实际调度 owner | ID 不重置；转移目标归属后仍能识别并取消旧身份通知 |
| sync_states | 每个目标的最后确认 revision、确认快照与本地修改序号 | 只在服务端明确确认后前移 revision |
| sync_outbox | 单调本地序号、owner、goal_id、operation_id、操作类型、快照、base_revision、尝试状态 | 操作 ID 唯一；请求一旦尝试就不可换内容后复用 |
| sync_conflicts | 本机、远端双方快照与版本、关联操作、解决状态 | 未解决前暂停该目标，不删除任一方 |
| identity_state | 当前 owner、身份代次和中断可恢复的切换状态 | 单例；不存 token 或验证码 |
| guest_transfers | 明确迁移请求的 ID、目标 owner、涉及目标集合与结果 | 重试同一请求不再次迁移新的访客记录 |

访客新建同样获得 UUID，但不创建网络待发送操作。仅有本地状态不显示待同步。
所有账号查询均带 owner 限定；outbox 读取还核对关联目标的真实 owner。
不得把任意排队项交给当前“恰好已登录”的账号发送。

### v2 升级

迁移在事务内完成：为旧目标分配 UUID，逐表保留旧数据，补调度 owner，
创建同步/身份表并初始化为 guest、revision 0。不得生成上传操作。
v1 先补原 v2 的 reminder_occurrences，再进行 v3 迁移。
不支持的版本显式失败，不能清库或建立替代空库来隐藏错误。

测试对比旧六张表的每个原列，包括 owner、归档、历史、false 打卡、
提醒 revision/needs_reconcile/status、通知 ID/armed/ended；
验证新 ID 唯一、外键、文件重开、失败回滚、无 outbox。
模拟器与真实安装的升级前后只读对照是另行证据，不由这些测试替代。

## 操作与原子性

### 2026-10-20 本地 v5 与目标文档 v2

AI 对话规划工作包在本地 `goal_schedules` 增加可空的 `start_minute`（0-1439）和
`duration_minutes`（5-480）；两者同时存在时结束不得超过 24:00。它们随 `effective_day`
版本化：习惯修改次日生效，单次修改当日生效；明确清除写为 null，不改写旧日期版本。
v1-v4 升级保留所有旧列，旧排期两字段均为空；迁移不新增上传操作。

新产生的目标聚合使用 `version: 2`，每条 schedule 必须包含上述两个键，值可为 null。
解析器继续读取 v1，内部比较和新快照统一为 v2。v1 中缺失字段不代表删除已有时间；
若旧服务器快照会丢掉已存时间，本地拒绝应用，保留当前数据。v2 显式 null 可表示清除。
已经持久化的旧 outbox 原文不改写，重试序列化仍保留来源版本及原键集合，不能把同一
`operation_id` 的 v1 请求换成 v2。新操作使用新的 ID 和 v2 内容。

本次仅更新客户端文档与本地替身协议；未修改或部署 Supabase 迁移，G3 仍是云端前置。
未来接通远端前必须使服务端明确支持 v2，不能把本地测试当成线上兼容性证据。

会话、消息、设置、记忆、记忆撤销事件、计划提议/回执和提醒取消队列均不上传。
仅经本人确认创建的目标走既有私密目标/outbox 事务。整批撤销时，任何打卡行（包括
`completed=false`）都要求保留；从未尝试上传且无打卡的目标可以本地删除，清理其
子表与 pending outbox。已确认上传或有尝试/在途证据的目标改为归档，保留同步记录。
删除事务先写 `reminder_cancellations`，提交后按通知 ID、来源标记、owner、goal、day 取消并核对；
中断重排可能让系统保留同一发生项的旧时间/时区载荷，这两个可变字段不作为归属条件。
只有确认系统待触发队列中已消失才移除意图。失败和进程退出可重试，身份切换前也须处理，
不得取消 ID 相同但归属字段不同的通知。不增加服务端删除协议。

| 操作 | 本地事务 | 上传语义 |
| --- | --- | --- |
| create | 新目标/版本/本机提醒 + sync_state + outbox | 创建完整目标聚合 |
| edit | 变更标题/计划版本 + outbox | 设为提交后的完整版本集合 |
| set_completed | 设 true，固定 occurrence + outbox | 设为完成，不使用 toggle |
| set_uncompleted | 保留 false 状态 + outbox | 设为未完成，传播撤销 |
| archive | 保留数据并归档 + outbox | 归档，不物理删除 |
| import_guest | 全部选定访客记录改归属 + 逐目标 outbox + transfer 结果 | 目标 UUID 不变，revision 从 0 开始 |
| resolve_conflict | 保留冲突档案 + 明确选择后的聚合 + 新操作 ID | 以所见远端 revision 再做条件写 |

纯提醒修改不产生云端操作。重复点击导致业务状态没变化时不新增操作。
outbox 写入失败必须回滚同事务业务写入；提醒平台失败发生在提交之后，
只更新提醒错误状态，不撤回业务记录。

每个目标的操作按本地序号串行。排队时保留每次提交后的快照，不读取“发送时最新状态”
代替旧请求。首次发送前把当前已确认 revision 和请求一起持久化，
再调用远端；重试始终使用同一 operation_id、base_revision 和快照。
同目标后续操作只能在前项确认后取得新的 base_revision。
多个目标可分别推进，但首版允许用单个协调器串行，先保证正确性。

## 服务端模型与授权

| 表 | 关键字段 | 权限 |
| --- | --- | --- |
| goals | id UUID、owner_id、kind、created_day/at、archived_day/at、revision | RLS 仅本人可读 |
| goal_titles | goal_id、effective_day、title | 经父目标 owner 限定 |
| goal_schedules | goal_id、effective_day、weekdays、planned_day | 经父目标 owner 限定 |
| check_ins | goal_id、occurrence_key、完成状态及原始日期/事件快照 | 经父目标 owner 限定；单次全局唯一 |
| applied_operations | owner_id、operation_id、请求指纹、已提交结果 | 普通客户端不能直接改写 |

所有迁移与函数在 `supabase/migrations/` 入库，由 CLI 部署，不在后台手工改表。
关闭默认新表暴露不能替代显式 grants/RLS；所有业务表开启 RLS。
客户端可以读自己的记录，不能直接 insert/update/delete 绕过条件写函数。

受控写入函数从 `auth.uid()` 获取 owner；缺少身份拒绝，不接受 payload 中伪造的 owner。
访问既有目标前核验其 owner，不能用他人的 UUID 创建或覆盖对象。
函数固定安全 search_path、校验 JSON 结构/类型/大小/键集合与业务约束，
只授予所需调用角色，不返回其他身份的数据。
测试必须覆盖 B 对 A 的读取、写入、伪造 owner、函数调用及未登录调用。

## 服务端幂等与 revision

一次受控事务完成：

1. 验证身份和结构，对操作幂等键与目标的并发写入加事务级锁。
2. 查询 `(auth.uid(), operation_id)`。已存在且请求指纹相同则返回原结果；
   相同 ID 携带不同请求则拒绝，不作为新的操作执行。
3. 校验目标 owner。首次创建要求不存在且 base_revision=0。
4. 若请求与当前状态语义一致，返回服务端规范快照，不再增加 revision。
5. 否则要求 base_revision 等于当前 revision；不等则返回双方可解析的冲突结果。
6. 成功时原子写目标及子记录，revision 递增，并保存操作响应。
   失败或事务回滚不留下半个目标、半组历史或“成功”操作记录。

语义相同不是逐字节相同：同一天同 occurrence 的两次“完成”可忽略不同设备的
记录时间，保留服务端已确认的规范事件。单次任务不同实际完成日并不相同。
标题、计划、归档等真实内容不同不能被这个例外吞掉。
撤销与无有效完成是相同结果，但 false 记录仍须保留以传播已发生的撤销。

如果服务器已提交但响应丢失，客户端保留不可变请求；重启后重发返回原响应。
收到成功响应后，在本地事务中核对 owner、身份代次、操作 ID 和目标 UUID，
更新确认快照/revision 并完成该项。若还有更晚的本机修改，不用旧响应覆盖页面。
登录过期暂停；绝不把旧账号请求换上新账号 token 后重发。

## 拉取与恢复

通过只读受控函数取得本人一致性快照；首次阶段不靠 Realtime 作为唯一来源。
拉取数据携带 owner 校验、目标 UUID、revision 和全部历史，不以当前规则重算日期。
较旧快照不能覆盖新版本。无 outbox/冲突的目标可在事务中直接应用；
有待发送操作的目标保留本机工作副本，把服务器版本留作比较，不静默覆盖。

新设备使用新的本地自增 ID 关联相同 UUID 的目标，插入本机提醒偏好为关闭，
不复制对方的通知 ID 或系统队列。已有设备保留自己的提醒偏好。
拉取后触发本机提醒核对；归档目标不得继续提醒。
拉取/写入中断后重新执行，不把部分加载误记为全部已同步。
数据超出单次响应限制时必须引入稳定快照游标，不默默截断默认 1000 行。

## 冲突情形

| 并发情形 | 结果 | 解决规则 |
| --- | --- | --- |
| 同一目标同日都完成 | 幂等成功 | 保留服务端规范事件，双方变成确认状态 |
| 同一 occurrence 都撤销 | 幂等成功 | 不重复反转状态 |
| 一端完成、一端撤销 | 冲突 | 保留双方，明确选一个，再按远端 revision 提交 |
| 同一目标改成不同标题/频率/计划日 | 冲突 | 展示完整差异，不按手机时钟覆盖 |
| 不同历史键上的修改 | 不静默丢弃 | 首版可保守报聚合冲突，保留所有原快照再由本人选择 |
| 一端归档、一端修改/完成 | 冲突，默认保留归档 | 不因旧副本中的 archived=false 自动复活 |
| 不同目标各自修改 | 独立成功 | 不制造成员/目标之间的连带冲突 |
| 解决时服务端又前进 | 再次冲突 | 保留此前选择与最新远端版本，重新确认 |

冲突记录保留本机完整工作副本（含后续排队操作）、服务器副本、各自 revision。
该目标后续操作暂停，不阻止其他目标同步。解决使用新的操作 ID，
旧操作标为已被解决操作取代，保留追踪关系，不用新内容重发旧幂等键。
未确认前不得删掉双方数据或把冲突显示成已同步。

归档复活只有在本人明确选择、且所选未归档版本有可信服务端记录证明已在归档前
提交时才可能允许；手机时间或仅有 base_revision 不足以证明。
证据不足时保持归档并提示原因，不增加通用“恢复归档”功能。

## 访客迁移与身份切换

登录后不自动上传。用户选择“暂不”时，本机访客保持原 owner，零上传。
选择迁移时生成迁移请求 ID，事务内把当前访客目标整体移动到目标身份并创建 outbox；
已有目标 UUID、内部 ID、历史与本机提醒偏好均保留，guest 不再保留副本。
重试迁移请求只返回原结果，不能把随后新建的访客数据也自动迁走。

切换身份与提醒：

1. 冻结新的旧身份业务命令和同步启动，记录身份切换意图与代次。
2. 按 reminder_occurrences 中的实际调度 owner 和受控 payload
   取消旧身份的系统提醒，核对 pending 确实消失；不能调用 cancelAll 清除不相关请求。
3. 只有取消确认后才完成身份切换或迁移。失败保留可重试状态，
   不先显示“已退出/已切换”而让旧提醒残留。
4. 激活新身份对应的本地仓储/队列，按其设备偏好重新排程。
   中途进程退出后先恢复切换协议，再运行正常提醒。
5. 在途旧身份响应只可确认原 owner 的不可变操作，不进入新身份页面；
   所有回调核对代次，不允许新 token 继续发送旧队列。

退出有未同步提示；确认后会话从安全存储移除，原账号数据留在隔离区，回到 guest。
会话过期时保留该账号本地修改但暂停网络队列，重登同账号后继续。
身份切换、数据库恢复和提醒任务使用同一串行边界，避免取消与重排交叉。

## 错误与界面

| 类别 | 本地处理 | 对用户表达 |
| --- | --- | --- |
| 未配置/访客 | 不初始化网络 | 仅本机 |
| 网络断开/超时/5xx | 保留 outbox；重试采用有上限退避，可手动重试 | 待同步 N 项 / 同步失败，可重试 |
| 401/会话过期 | 暂停所属账号队列 | 需要重新登录；本机记录仍在 |
| 限流 | 遵守 Retry-After/退避，不循环发送验证码 | 稍后再试 |
| revision 冲突 | 保留双方，暂停该目标 | 两台设备的记录不一致 |
| 格式/权限拒绝 | 不自动改 owner 或删数据；记录脱敏错误类别 | 同步失败，保留记录 |
| 本地事务失败 | 回滚本次业务与 outbox；旧数据不变 | 保存失败，可重试 |
| 提醒平台失败 | 业务提交保留，独立修复提醒 | 原有提醒未确认/可重试状态 |

“已同步”要求当前身份的本地工作副本已得到服务端确认，且无待处理操作、
冲突或未完成拉取；不能由 SDK 连接成功或一次请求成功推导。
不会显示假账号、假成功、演示云记录或技术框架宣传。

## 验证分层

- P3：文件迁移、事务回滚、UUID、重复/丢响应/进程恢复、冻结请求、
  revision 冲突、同结果幂等、合并不覆盖 pending、账号隔离、提醒切换。
  远端替身只在测试目录，不进入正式版本。
- P2：真实 SMTP/邮箱/目标网络/最小 RLS。G3 不通过则不进入 P4。
- P5：真实服务端越权、两设备、离线、Keychain 会话、真实安装只读升级对照。
  替身全绿不能把 S05 至 S19 的设备或云端项标为通过。
- 服务端迁移需要空 dev 数据库可重放证据；没有 Docker 不省略这项，
  也不未经所有者确认去重置含未知数据的项目。
