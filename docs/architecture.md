评估日期：2026-10-07。

目标是把[产品方向](product-direction.md)变成可执行的技术基线。
以下是本轮推荐方案；“选用”表示后续实施的默认方案，不代表依赖已经加入主工程，
也不代表所有插件、服务或网络环境已经验证。涉及账号、付费资源和隐私规则的决定仍需用户确认。

## 选择结论

| 领域 | 首版选择 | 原因及代价 | 引入阶段 |
| --- | --- | --- | --- |
| 客户端 | 继续 Flutter 与 Dart | 保留现有工程，服务 iOS 优先与后续 Android；鸿蒙另行验证 | 已采用 |
| 状态与依赖管理 | Riverpod，先不使用其代码生成或实验性离线持久化 | 组织异步状态和测试替身；需要学习 Provider 生命周期 | M1 |
| 本地数据 | Drift 与 SQLite，提交 schema 迁移及迁移测试 | 目标、记录、提醒、待同步操作有关系和唯一约束；付出 SQL 与生成代码成本 | M1 |
| 导航 | 单页面阶段保留 Navigator；多页面和邀请链接阶段使用 go_router | 不提前引入复杂路由，后续集中处理页面状态与入口 | M2 |
| 个人提醒 | flutter_local_notifications，配合 timezone 和 flutter_timezone | 插件处理平台通知接口，应用负责日期规则与调度；必须真机验证 | M1 |
| 后端默认方案 | Supabase Auth 与 PostgreSQL，加 RLS、受控数据库函数和必要的 Edge Functions | 减少账号和基础运维工作，保留关系模型与服务端权限开发；受网络、邮件和供应商约束 | M3，通过验证关卡后 |
| 登录形式 | 首版默认邮箱验证码，使用 Supabase Auth，不自建密码系统 | 减少密码管理界面，但邮件投递与限流是硬依赖；必须先验证自定义 SMTP | M3 |
| 云端接入 | supabase_flutter | 使用服务端身份与数据库接口，不将其误当作离线同步引擎 | M3 |
| 同步 | 本地数据库与 outbox，加服务端幂等写入和版本检查 | 明确处理断网、重试、撤销、冲突；这是需要自行实现和测试的业务能力 | M3 |
| 自动检查 | 延续 GitHub Actions，逐步加入迁移、权限及 iOS 构建检查 | 现有 Linux 检查保留；Mac 构建耗时与额度单独核算 | 按阶段添加 |

能力依据：[Flutter 架构指南](https://docs.flutter.dev/app-architecture/guide)、
[Riverpod 文档](https://riverpod.dev/docs/introduction/getting_started)、
[Drift 文档](https://drift.simonbinder.eu/)、
[go_router](https://pub.dev/packages/go_router)、
[通知插件](https://pub.dev/packages/flutter_local_notifications)、
[Supabase Flutter SDK](https://pub.dev/packages/supabase_flutter)。

## 为什么不选其他路线

| 替代方案 | 本轮不选的原因 | 何时重新考虑 |
| --- | --- | --- |
| SwiftUI 原生重做 | 与已有 Flutter 工程及 Android 目标不一致，会增加两套界面维护 | 明确改为 Apple 专用，或出现无法接受的平台限制 |
| 只用 setState 管理整个应用 | 适合当前演示，不适合同时表达本地记录、账号和同步状态 | 局部临时界面状态仍然使用，不将其全面禁止 |
| 只用键值存储保存全部数据 | 首版已有日期查询、关联、唯一约束和迁移需求 | 只用于非敏感偏好，不作为打卡主数据库 |
| Firestore 作为主数据源 | 本项目优先关系型小组权限与独立本地数据库；避免同时学习另一套数据模型 | 若实际需求更偏向其离线与生态能力，再对照迁移代价评估 |
| NestJS 与 PostgreSQL 自建全套后端 | 对目前个人项目增加认证、部署、邮件、备份和运维工作 | 用户明确以服务器后端岗位为学习目标，或托管方案不满足实际网络与部署要求 |
| 一开始引入完整同步服务或 CRDT | 当前数据和协作模式不需要多人共同编辑同一目标，先控制问题范围 | 多端冲突需求扩大、手写同步成本超过服务引入成本 |

这是针对本项目的工程取舍，不是通用的框架优劣排名。
选择托管后端也必须编写数据模型、授权策略、接口约束和测试，不能把这些工作省略成“连上云即可”。
若更换后端方案，要重新估算 M3，不能认为保留 PostgreSQL 就无需重做接口和认证。

## 客户端结构

按业务功能组织目录，内部区分页面、状态控制和数据访问：

```text
lib/
  app/                 应用入口、主题、导航与初始化
  features/
    goals/             个人目标与打卡
    reminders/         提醒设置与调度
    review/            历史与个人成就
    account/           登录与账号切换
    circle/            小组与授权共享
  data/
    local/             Drift 表、查询和迁移
    remote/            云端接口适配
    sync/              待同步队列、重试与冲突处理
  shared/              确实被多处复用的组件和时间类型
```

这是实施时的目标结构，本轮不创建空目录或把现有单页面强行拆成大量类。
页面不直接写 SQL 或判断小组权限。时间和通知接口应可替换，以便测试跨日、
拒绝授权和网络错误，不依赖真实等待。

## 数据模型

| 数据 | 关键字段或约束 | 隐私要求 |
| --- | --- | --- |
| 目标 | id、owner、类型、标题、重复规则、时区、归档时间、revision | 默认本人可见 |
| 打卡 | goal_id、所属日期、期望状态、revision；同一目标日期唯一 | 只由本人修改，备注不混入共享进度 |
| 私人记录 | goal_id、正文、创建时间 | 独立保存和授权，不因共享目标自动可读 |
| 提醒设置 | 本地身份、goal_id、时间、启用状态 | 首版按设备生效，不让另一台设备改动造成重复提醒 |
| 调度记录 | 通知 id、目标和发生日期、计划时间、调度状态 | 用于取消、重建和排查，不存私人正文到通知载荷 |
| 待同步操作 | 本地身份、operation_id、对象 id、base_revision、期望状态 | 和业务写入在同一本地事务保存 |
| 小组与成员 | group_id、user_id、角色、成员状态 | 不能由客户端伪造成员关系 |
| 共享授权 | goal_id、group_id、共享字段范围、生效时间、撤销状态 | 不把加入小组等同于全部历史公开 |
| 动态与回应 | group_id、作者、正文、关联目标可空 | 作者与小组授权均在服务端验证 |

本地访客与每个登录账号使用独立数据命名空间。首次登录时明确选择是否迁移本机访客数据；
迁移可重试且不能重复创建记录，不能在登录事件里静默上传所有本地内容。
日期归属与事件发生时间分开保存，避免跨时区后把历史打卡移动到另一日。
具体补签范围和时区体验按产品规则确认后实现，不由数据库设计偷定产品行为。

## 同步协议

1. 本地事务保存业务数据和 outbox 操作，页面立即反映本地结果，显示待同步状态。
2. 登录且网络可用时上传；发送“设为完成”或“设为未完成”，不发送容易被重试反转的 toggle。
3. 服务端验证账号、对象所有者和操作类型，以账号加 operation_id 防重复执行。
4. 按 base_revision 检查冲突；成功返回服务端 revision。删除和撤销也必须可同步。
5. 成功确认后才清理待同步操作；网络中断可重试。过期登录暂停队列，不转交给新账号。
6. 首版优先拉取本人数据快照并按版本合并，不立即建设复杂增量变更流。
   拉取不能覆盖尚未上传的本地修改；数据扩大后再设计分页一致性和可靠游标。
7. 冲突保留双方数据并要求明确解决，不依靠手机时间戳决定谁覆盖谁。
8. 小组内容重新获取时必须再次授权；撤销权限后清理不再可见的缓存。

前台恢复、手动刷新和写入成功触发同步。Realtime 最多用作“需要刷新”的信号，
不能作为唯一交付保证，也不承诺 App 长期在后台仍保持即时同步。
参考：[Flutter 离线优先指南](https://docs.flutter.dev/app-architecture/design-patterns/offline-first)。

## 服务端授权

- 所有客户端可访问的业务表都必须有明确授权策略，默认拒绝未授权请求。
- 本人私密数据和共享给小组的投影分开。共享接口只返回白名单字段，不返回完整私人记录后让 UI 隐藏。
- RLS 处理行的访问；不能假设行级授权会自动隐藏同一行中的私人备注。
- 邀请加入、撤销共享和账号清理等多步操作通过受控事务或服务端函数执行。
- 使用具备提升权限的函数时，必须限制调用者、执行路径和返回字段，并补越权测试。
- 手机端仅持有适合公开客户端的项目配置和用户会话，不包含管理员密钥。
- 会话持久化接入平台安全存储适配，日志不输出 token、日记或原始通知正文。

权限测试使用本人、同组成员、非成员和未登录请求分别检查读取和写入；
覆盖伪造 owner_id、撤销共享、退出小组、过期邀请和账号切换。
参考：[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、
[数据库测试](https://supabase.com/docs/guides/database/testing)。

## 提醒是独立风险项

已确定使用本地通知插件，不依赖云端推送来实现个人提醒。
但插件不替我们决定重复规则、撤销后恢复、时区切换和调度上限。
其维护者文档列出了 iOS 待调度通知 64 条的限制及基于时区的调度接口；
该边界需在目标 iOS 版本验证，而不是按无限容量设计。
来源：[通知插件限制与调度说明](https://pub.dev/packages/flutter_local_notifications)。

当前产品要求同时包含“完成当天后取消当天提醒”和“未来重复提醒保留”。
不能只创建一个无限重复通知，再以取消全部重复通知的方式处理完成状态。

在 M1 前用 4 至 6 小时做专项验证：

1. 验证本地按日期通知、固定 id 更新、取消和通知权限状态。
2. 对比重复日历通知与按发生日期排队的方案，验证跳过本次且保留未来是否成立。
3. 按发生日期排队时，明确全局待调度容量、覆盖到哪一天及补充时机；
   不能假设无限后台补充，不能把“以后每天都会提醒”写成未经验证的承诺。
4. 真机测试后台、离线、已完成、修改时间、归档、重新打开以及时区变化。
5. 若必须以有限覆盖窗口换取精确取消，要先让用户接受这个限制并修改验收；
   未确认前不悄悄降低原来的提醒要求，也不把提醒阶段标为完成。

这是有明确时间预算和退出条件的技术验证，不是继续把“提醒怎么做”无限期搁置。

## 云端部署与验证关卡

默认评估 Supabase 托管项目。先开发环境，后真实使用环境；迁移脚本进入 Git，
禁止只在后台手工改表而没有可重复的变更记录。后端函数随迁移或独立版本部署，
手机端通过接口访问，GitHub 不承担线上数据库。

正式创建资源前确认用户预算、实际使用地区与网络、邮箱服务及数据部署要求。
网络与认证验证预算 4 至 6 小时，包含：

- 在目标 Wi-Fi 和移动网络中测试注册、登录、刷新会话、读写和失败恢复。
- 验证两个真实测试邮箱的收信和验证码过期行为，不能只测自己的管理员邮箱。
- Supabase 默认 SMTP 有收件人限制且不面向正式生产；邮件登录需要把自定义 SMTP
  配置和投递验证计入任务。来源：[官方 SMTP 说明](https://supabase.com/docs/guides/auth/auth-smtp)。
- 完成至少一组 RLS 允许和拒绝测试，再实现多人 UI。

网络、费用或邮件投递不合格时，暂停云端接入并重新评估部署方案。
这不会阻止个人离线版交付。2026-10-10 已按所有者确认创建免费 Supabase 开发项目，
初始区域为新加坡，尚未接入 App 或通过 G3；未购买邮件服务，不承诺长期零运行成本。
创建配置、凭据保管与剩余验证见[云端开发环境记录](cloud-setup.md)。
